# 拜访录音 → 销售易

把一条客户拜访录音（录音豆同步到飞书后生成的妙记）整理成**销售易跟进记录**，必要时**推进商机阶段**。
**写入前必须让销售确认；只有销售本人确认过，才允许改商机阶段。**

所需能力（任选其一可用的方式）：
- 读妙记：「飞书妙记」连接器；或 `lark-cli minutes +search / +detail --summary --transcript`（user 身份）
- 销售易：「销售易 CRM」连接器（即销售易 MCP，工具名形如 `entity-search` / `entity.search`）

## 1. 找到妙记

- 用户给了妙记链接：`minute_token` 是链接 `/minutes/` 后面那段。
- 用户说"刚才/今天的拜访"，或定时任务触发：查找当前用户今天新生成的妙记（录音豆录音也会生成妙记）。
  有多条时逐条处理；已经处理过的跳过——判据是**台账里已有同一妙记链接的记录**（处理状态为待确认 / 已写入 / 已忽略 / 写入失败都算已处理），或销售易里该商机已有引用同一妙记链接的跟进记录。

### ⚠️ 妙记读不到时，走录音豆多维表（这条必须先看）

**录音豆的录音不一定对当前账号开放妙记读取权限。** 录音豆由别人录制时（录制人不是任务发起人），妙记 owner 是那位录制人，`minutes +detail` 会返回 `No read permission for minute ...`。这种情况下**不要就此跳过**——录音豆自己的同步流程会把录音写进多维表格，那里有完整内容且通常可读：

- Base「录音的汇总统计」`{{recording_base.base_token}}`，表「**录音信息整理**」`{{recording_base.recording_table_id}}`。
  （本技能里的 `{{recording_base.…}}` 由部署脚本从 `config/app.json` 的 `recording_base` 段填入。如果看到的还是 `{{…}}` 原样，说明拿的是仓库原文件，去 `config/app.json` 里取对应的值。）
- 关键字段：`录音时间`、`录音内容总结`（完整 AI 总结）、`智能纪要链接`、`录音逐字稿`（指向文字记录文档的链接）、`妙记链接`、`录音ID`、`录制人`、`录制人部门`、`录音时长`。
- **`录音分析` 是 lookup 字段，值来自「AI输出结果明细」表**（`{{recording_base.ai_result_table_id}}`），格式是【会议主题 / 价值传递 / 客户反馈 / 下一步计划 / 其他值得注意的信息】。
- 逐字稿/智能纪要链接是云文档，用 `lark-cli docs +fetch --doc <链接URL> --doc-format im-markdown` 直接读，**这条路径通常比妙记权限更宽**。

所以正确顺序是：**先查台账去重 → 反查录音信息整理表（按当天录音时间）→ 有对应录音就用它的总结+逐字稿整理 → 妙记链接照抄表里的值。** 只有当表里也没有这条录音时，才算真的取不到内容。

读不到妙记时**不要一直重试**（重试不会改变权限结果）；按需用 `minutes +apply-permission --minute-token <tok> --perm view` 申请一次读取权限，申请完仍未开通就继续走多维表路径。

## 2. 读内容

读这条妙记的 **AI 总结** 和 **逐字稿**（妙记没权限时按上节走录音信息整理表，读 `录音内容总结` + `录音逐字稿`/`智能纪要链接` 指向的文档）。逐字稿的说话人标签可能不准，按语义判断谁是销售、谁是客户。
内部会议、培训、闲聊、设备测试等**非客户沟通**：告诉用户「这条不是客户拜访，已跳过」，不写 CRM、不建台账。

## 3. 整理跟进内容

只写录音里真实出现的信息，**不编造**数字、时间、人名。格式：

```
拜访时间：<妙记录音时间>
【拜访纪要】（AI 整理自录音豆妙记）
客户联系人：张总、李工（技术负责人）
沟通要点：1. … 2. …
客户需求与顾虑：1. …
达成共识：1. …
下一步：1. （时间 + 负责人 + 事项）
妙记：<妙记链接>
```
同时判断：
- 跟进方式：拜访 / 线上会议 / 电话
- 意向程度：0 无意向 / 1 略有意向 / 2 意向一般 / 3 意向较高 / 4 意向极高

## 4. 在销售易里找客户和商机

1. `entity-search`：entity=`account`，keyWord=录音里的公司名，conditions 加 `{apiKey: "ownerId", type: 1, value: <当前用户销售易ID>}`，只在**本人负责**的客户里找。
   先用全称，找不到再去掉「有限公司 / 科技 / 智能」等后缀逐步放宽。当前用户的销售易 ID 用 `user-detail`（不传参数）获取。
2. 客户唯一 → `entity-search`：entity=`opportunity`，conditions `{apiKey: "accountId", type: 1, value: <客户ID>}`，**按最近更新排序取全部商机，不要先按状态过滤**。商机状态只有三个：`status=1` 进行中、`2` 赢单、`3` 输单。
   **赢单商机照样要跟**：合同签完还有交付、验收、售后、复购、增购这些现场拜访，活动记录也要挂在原商机上。所以赢单商机是**正常的挂载对象**，不是被排除的对象。
3. 选商机的顺序：
   - 有 `status=1` 的进行中商机：取最近更新的那个。
   - 只有赢单（`status=2`）：取最近更新的那个，并明确告诉销售「这条商机已经赢单，跟进记录挂它、不再改阶段」。
   - 同时有进行中和赢单：优先进行中；但如果这次拜访明显是交付 / 售后 / 复购性质，或客户明确提到已签的合同，改挂那条赢单商机，并在确认时说明选择的理由，让销售可改。
   - 只有输单（`status=3`）或完全没有商机：跟进记录只挂客户，不谈阶段。
   - 找到 0 个或多个客户：列出候选让用户指定，**不要猜**。
   - 多个同状态商机：默认最近更新的那个，并在确认时让用户可改。
   - **不新建**客户、联系人、商机。

## 4b. 提取商机情报（MEDDPICC）

按 MEDDPICC 八项从逐字稿里提取。**每一项都必须能逐字引用客户原话**；没谈到、只能推测、或只是销售自己说的，一律记为「未知」，不要猜。

| 项 | 要摸清什么 |
|---|---|
| 痛点 | 客户现在的问题，以及不解决的后果 |
| 量化收益 | 客户希望达到的可衡量结果（排队时长、人力成本、转化率…） |
| 经济决策人 | 最终拍板、掌握预算的人 |
| 决策标准 | 客户评估方案的标准（技术、价格、交付周期、安全…） |
| 决策流程 | 从评估到拍板经过哪些人、哪些步骤、什么时间 |
| 采购/合同流程 | 招标、采购、法务审合同、盖章付款等环节和周期 |
| 内部支持者 | 客户内部明确支持我们、愿意帮我们推动的人 |
| 竞争 | 客户同时在看的其他供应商，或自研、维持现状 |

另外单独提取三样能回填销售易的信息：
- **预算**：客户明确说出的金额（元），「三十万左右」= 300000；没说数字就不填。
- **关键人角色**：先 `entity-search` entity=`contact` conditions `{apiKey: "accountId", type: 1, value: <客户ID>}` 拿到该客户已有的联系人（姓名、职务、联系人角色），把「张总」「李工」按姓氏 + 职务对应上；同姓多人或对不上就不对应。角色只能是销售易「联系人角色」的选项：决策者（拍板/掌握预算）、审批者（签字但不主导选型）、评估者（技术或业务评估）、用户、权力支持者（有影响力且支持我们）、其它。
- **竞争对手名称**。

把结果作为跟进记录的一节，放在「下一步」之后、「妙记」之前：
```
商机情报（MEDDPICC）：
· 痛点：…
· 经济决策人：…（只列摸清了的项）
待摸清：采购/合同流程、内部支持者
下次可以问：
1. （针对最要紧的 2–3 个待摸清项，销售下次能直接开口问的问题）
```

## 4c. 生成「建议更新」（只在挂到商机时）

能落到销售易字段的，生成「改前 → 改后」建议，**每条先用 `dryRun: true` 预检**，预检不通过的不列为建议，只在确认时说明原因：
- 预算：`entity-detail` 读商机 `projectBudget`，不同才建议；写入 = `entity-update` entity=`opportunity` fields `{projectBudget: <数字>}`。租户编辑表单里没有该字段时会报「不存在」，告诉销售「需要管理员把项目预算加到商机页面布局」。
- 联系人角色：只针对**已有**联系人且角色不同的；写入 = `entity-update` entity=`contact` recordId=联系人ID fields `{contactRole: "<选项名>"}`。销售易里没有这个人就说明「没有对应联系人，未新建」。
- 竞争对手：`entity-search` entity=`competitorProfile` keyWord=名称，唯一命中且该商机还没关联（`entity-search` entity=`opportunityCompetitor` 按 opportunityId 查）才建议；写入 = `entity-create` entity=`opportunityCompetitor` fields `{name, opportunityId, competitorProfileId, accountId, competitiveStatus: "活跃"}`。库里没有就说明「不在竞争对手库，未新建」。
- **不新建**联系人、竞争对手档案。

## 5. 判断商机阶段（保守）

- 用 `opportunity-stageInfo`（id=商机ID）读取该商机的阶段列表和当前阶段，**不要自己编阶段名**。
- 只有客户**明确表态**（明确要正式报价、确认预算并要走采购、进入商务谈判）才建议推进；模糊意向一律不动。
- 必须能从逐字稿里**逐字引用客户原话**作为依据，引用不到就不建议。
- 只在进行中阶段之间变化；**永远不要建议赢单 / 输单**。
- **商机已经赢单（status=2）或输单（status=3）时，一律不建议改阶段**：流程已经结束，这次拜访只写跟进记录。跟进内容里可以写交付、验收、售后、复购的进展，但不碰阶段。

## 6. 让销售确认（必须）

把以下内容发给销售（飞书消息或卡片），等待明确答复：
- 客户 / 商机 / 当前阶段
- 跟进内容全文
- 建议阶段 + 客户原话依据（如有）
- **建议更新（如有，仅挂商机时）**：逐条「改前 → 改后」+ 客户原话依据；以及没法自动更新的项和原因（例如租户表单里没有该字段、联系人库里没有这个人）
- 选项：**确认写入**（跟进 + 阶段 + 建议更新一起执行）/ **只写跟进记录**（不改阶段、不回填字段）/ **修改**（用户说改哪里、去掉哪条，改完再给一次）/ **忽略**

**没有确认就不写入**：超过 24 小时没答复，提醒一次；仍没答复就放着，**任何情况下都不替销售写入**；台账对应的记录保持「待确认」，不改状态。

## 7. 写入销售易

确认后：
1. `followup-create`：`content`=跟进内容，`parentEntity`=`opportunity`（无商机时 `account`），`parentRecordId`=ID（字符串），`entityType`=拜访类活动记录类型 ID（`metadata-entityBusinessTypes` entity=`activityrecord`，选 apiKey=`busitype_visitsign` 或名称含「拜访」的），`intentionalDegree`=`"0"`–`"4"`。
   **业务类型的叫法每个环境都不一样，必须现场读，不能套用记忆**：页面上的「现场拜访」「线上拜访」「电话拜访」是**业务类型的名字**，有些环境里就是独立的业务类型（标签直接叫「现场拜访」），有些环境里则只有「拜访签到」`busitype_visitsign`、页面叫法只是别名。**不要因为某个环境里没有叫「现场拜访」的业务类型，就断定别处也没有。**
   - 写入前先 `metadata-entityBusinessTypes`（entity=`activityrecord`）把当前环境的业务类型全列出来，按**语义**挑最贴近的那个（现场 → 拜访签到 / 现场拜访；线上 → 线上拜访 / 视频会议）。
   - 挑到的类型如果和销售说的类型对不上，**在确认环节说明**「你说的『现场拜访』在这个环境里对应的是『拜访签到』」，让销售知情后再写，不要默默换类型。
   - 如果当前环境确实只有「线上拜访」类、没有现场类，**不要拿线上冒充现场**——类型会失真，拜访形式/签到合规/统计口径全错。这种情况按下面「阶段被挡住时怎么走」的第 5 条给销售选项。
2. **`saleStageId`（商机阶段）的取值方式，按当前环境实测，不要套用别处结论**：
   - 记录归属的商机后，服务端通常会把阶段对齐成**该商机的当前阶段**；**正常情况直接不传这个字段**最省事，挂客户（没有商机）时同样不传。
   - 但这条已被验证得比较强的前提是「字段允许留空」。**在把阶段留空当成通用做法之前，先确认当前这个业务类型里 `saleStageId` 到底是不是真必填**（`metadata-entityDescribe` 看 `required`，再用 `metadata-fieldOptions` 看能不能取到可选阶段集合）。不同环境、不同业务类型的表单配置并不一样。
   - 只有服务端报「必填缺失」或「阶段不可关联」时，才按下面「阶段被挡住时怎么走」处理——**不要因为别处跑通过就断定这里也能跑通**，也不要反过来因为别处报错就认定这个环境也写不进。
3. 用户同意改阶段时：`opportunity-advanceStage`。
   - 每一步先 `dryRun: true`；`blockers` 非空就停下，告诉用户原因（审批 / 关键信息字段），不要强推。
   - `opportunity-stageInfo` 里 `adminSetting.canGoto=0` 表示**不允许跨阶段**：从当前阶段的下一个开始**逐级推进**到目标阶段。
   - 赢单 / 输单不走这个工具。
4. 用户同意的**建议更新**（4c）：按 4c 的写法逐条执行，执行前再 `dryRun` 一次。某条失败不影响其他条，也**不回滚**已写入的跟进记录——逐条如实回报成败。
5. 回报：跟进记录 ID、阶段变化路径（如 初步接洽 → 需求确定 → 方案/报价）、每条建议更新成功 ✓ / 失败 ✗ 及原因。
6. 写入失败：说明原因，**不要自动重试**，避免写出重复记录。

### 销售阶段被挡住时怎么走

**先判断环境，再判断原因。** 生产环境和测试/沙箱是**两套独立配置**：业务类型（页面上的「现场拜访」「线上拜访」这类）、阶段档位（有的环境是「初步接洽→输单」6 档，有的是「1…8 合同归档」这类编号流程）、以及每个业务类型里阶段字段是必填还是可选，都可能完全不同。**在自己环境跑通的结论不能推给别人的环境，反之亦然。**

报「必填缺失」或「阶段不可关联」时，按下面顺序查：

1. **确认自己在哪套环境**：`user-profile` 的 `tenantSettings.company` 会直接写出公司名（例如「测试环境-公有云需求」就是测试环境）。先确认这次要写的是不是这套环境的目标，别在测试环境里替生产环境排障。
2. **看那个业务类型的阶段字段到底怎么配的**：`metadata-entityDescribe`（带 `busiTypeId`）看 `saleStageId` 的 `required`；`metadata-fieldOptions` 看这个业务类型能取出哪些阶段。
   - 取不到选项（`total=0`）通常意味着**该字段的候选受流程/过滤条件约束**，只能从商机当前流程里选——这种限制是元数据层面锁死的，**换传 ID、传对象、只传名称都绕不过**。
   - `required=true` 而候选又取不到，就是死结：接口层面拿不到合法值，只能在界面提交。
3. **核对是不是挂错对象**：确认要挂的商机确实是这条、它的当前阶段是什么（`opportunity-stageInfo` 的 `currentStageId` / `currentStage`）。报错里出现的阶段名如果在本环境的 `opportunity-stageInfo` 里根本不存在（例如「8 合同归档」不在 6 档流程里），那它属于**另一条商机或另一套流程**，先纠正挂载对象。
4. **再看商机本身**：已输单、被锁定、审批中、或不在本人负责范围，都可能让表单拒绝关联。
5. 以上都不成立时，**不要为了绕过去乱填或硬塞阶段**，写进去的数据就是错的。把真实原因说清楚——哪套环境、哪条商机、当前什么阶段、报错原话、卡在哪一步——然后给销售两条出路：
   - 在 CRM 界面手动提交这条记录（界面和接口是两套校验，接口卡住不等于界面也卡）；
   - 或者这次只把内容**挂到客户**（`parentEntity`=`account`），先保住内容不丢，等流程或表单配置调整后再补挂。
6. 选后者或最终没写成时，台账记 `处理状态=写入失败`，原因写进「问题与支持」。**不要自动重试。**
7. 商机已赢单（`status=2`）时阶段本就不该再动：跟进记录照常挂这条赢单商机，只是不建议推进阶段。

**跨环境求助的边界**：别人环境里的报错，如果我没拿到那套环境的授权，就只能做诊断、不能动手改。要说清「我只连了哪套环境、那套里有什么」，不要把自己环境的元数据当成对方的配置去下结论。

## 8. 归档到多维表格台账（每条客户拜访都写）

台账是这条链路的**唯一状态源和去重依据**，写在确认环节之前，不要等销售易写完再补。

- Base：`{{recording_base.base_token}}`（「录音的汇总统计」），表 `{{recording_base.ledger_table_id}}`（「拜访跟进台账」）。
- 身份：写 Base 必须用 `--as user`。`--as bot` 会返回 `91403 Forbidden`，不要用 bot 重试。
- **处理人（必填，用来定位「谁跑的这条流程」）**：人员字段 `处理人`（`fldVYUm4P2`，单选），填**本次真正执行处理的飞书账号**——不是录音的录制人，也不是客户联系人。
  - 取自己的 open_id：`lark-cli api GET /open-apis/authen/v1/user_info --as user`，返回里的 `open_id` 就是当前执行账号。**不要按姓名搜**（`contact +search-user` 可能撞同名，也会查到别人）。
  - 写法 `[{"id":"ou_xxx"}]`，该字段 `multiple=false`，只填一个。
  - 为什么单列：录音的「录制人」在录音信息整理表里（`录制人` 字段），处理人在台账里。别人录、我处理时这两个人不同，只有分开记才能定位到是谁跑的。
- **录制人（必填，照抄来源）**：人员字段 `录制人`（`fldDHh9R6X`，单选），值直接照抄「录音信息整理」表同一条录音的 `录制人`，不要自己推断。
  - **两列一比就看出跨人**：`录制人` ≠ `处理人` = 别人录、我来处理（跨人操作）；两者相同 = 录制人自己处理的。
  - 来源表没有录制人（或走的是妙记检索、拿不到录制人）时留空，不猜。
- 时机与状态流转：
  1. 整理完、准备发给销售确认时 → 建记录，`处理状态=待确认`，填下面这组字段。
  2. 销售确认并写入销售易后 → 同一条记录 update 为 `处理状态=已写入`，补 `销售易跟进记录ID`，并把 `商机情报（MEDDPICC）` 更新成**销售最终确认的版本**（销售改过哪项就按改后的写）。
  3. 销售选「忽略」→ `处理状态=已忽略`。
  4. 写入销售易失败 → `处理状态=写入失败`，`销售易跟进记录ID` 留空；不要自动重试。
- 填哪些字段（对齐《录音豆数据同步销售易方案》的同步字段口径）：
  - **必填**：客户名称、商机、拜访目的、客户联系人、拜访时间（= 录音时间）、跟进内容（= 活动记录内容，附妙记链接）、跟进方式、意向程度、处理状态、妙记链接、**处理人**（本次执行账号的 open_id）、**录制人**（照抄录音信息整理表）。
  - **可选**：客户方其他人员、我司协访人员、商机推进情况、问题与支持、下次沟通日期、下次行动计划、建议阶段、客户原话依据、**建议更新**（4c 生成的「改前 → 改后」逐条，含预检不通过的项和原因）。
  - 录音里没出现的内容**留空**，不要填「未知 / 待补充」这类占位词，也不要推测。
- **`商机情报（MEDDPICC）`**：每条都填，存 4b 提取结果的 JSON。销售画像工作台（`visit-to-persona` 技能）直接用这份销售确认过的结果，不再重新提取，所以格式要照下面写：
  ```json
  {"opportunityId":"<销售易商机ID，只挂客户时为空串>","accountId":"<销售易客户ID>",
   "fields":{"pain":{"known":true,"summary":"…","quote":"客户原话，逐字"},
             "metrics":{…},"economic_buyer":{…},"decision_criteria":{…},
             "decision_process":{…},"paper_process":{…},"champion":{…},"competition":{…}}}
  ```
  八个键对应 4b 的痛点、量化收益、经济决策人、决策标准、决策流程、采购/合同流程、内部支持者、竞争，八个都要有。没摸清的写 `{"known":false,"summary":"","quote":""}`。`quote` 必须是逐字稿里客户原话的原样片段，不改字、不加标点。
  - 台账里还没有这个字段时，先建一次（文本字段），再写记录：
    `lark-cli base +field-create --base-token {{recording_base.base_token}} --table-id {{recording_base.ledger_table_id}} --as user --json '{"name":"商机情报（MEDDPICC）","type":"text"}'`
- 只写客户拜访。内部会议、培训、闲聊**不建台账记录**（跳过即可，不要让台账被非客户内容污染）。
- 不写 `归档时间`（created_at 系统字段，自动生成）；不写公式字段。
- 命令（字段名照抄，select 传数组）：

## 权限

| 操作 | 所需 |
|---|---|
| 读取妙记 | 飞书妙记连接器（或 lark-cli user 身份：`minutes:minutes.search:read` `minutes:minutes.basic:read` `minutes:minutes.artifacts:read`） |
| 查客户 / 商机 / 联系人、建跟进、推进阶段、回填预算 / 联系人角色 / 竞争对手 | 销售易 CRM 连接器（销售本人 OAuth 授权；授权页选对环境：生产 / 沙箱） |

**一次授权只绑定一套环境。** 授权时选的是哪套，后续所有查询和写入就都在那套里——不是「同一个账号能看到两边」。判断当前连的是哪套：`user-profile` 的 `tenantSettings.company`（例如「测试环境-公有云需求」= 测试环境）。

所以出现「我这套环境里查不到那条记录」时，先想清楚是**根本没有**，还是**在另一套环境里**。要跨环境操作，只能让对应环境的账号重新授权，不能靠换查询条件绕过去。
